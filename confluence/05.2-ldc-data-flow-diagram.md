# LDC Premises Data Flow - Detailed Workflow

## Overview

The LDC premises pipeline operates on a monthly cadence, fetching the latest Snowflake snapshot, upserting into the accumulated PostgreSQL raw table, re-transforming the full history, and publishing cleaned output. This page documents both the legacy (AS-IS) flow and the current production flow.

## AWS Step Functions Workflow Structure

### Step Functions Orchestration

```
AWS Step Functions (Monthly Trigger or Manual)
└── Single Step: LDC Premises Batch Job
    ├── Job Definition: hsds-ldc-premises-job
    ├── Job Queue: hsds-e2e
    ├── Container: ECR (highstreets:latest)
    └── Entrypoint: poetry run python highstreets/aws_pipeline/ldc_premises_e2e.py
```

### Job Queue & Environment
- **Queue**: `hsds-e2e` (shared with BT and Mastercard pipelines)
- **Compute Environment**: Auto-scaling with container optimization
- **Error Handling**: Step Functions retry with exponential backoff
- **Monitoring**: CloudWatch integration for real-time status

### Container Environment Variables

## Upsert Strategy Detail

### How Change Detection Works

Snowflake Fetch (source='live') plus ro_hash --> Staging Table (truncate + append) --> Raw Table (accumulated) --->
Upsert outcome: 1. New PK → INSERT
                2. Same Hash →  SKIP
                3. Diff hash →  UPDATE

### Why Full Re-Transform?

The clean table is fully reloaded each run (not incrementally updated) because:

1. **Cross-row dependencies**: `fix_premises_dates` examines all records at a premises to correct date sequences; changing one record can affect adjacent records
2. **Forward-fill logic**: `_forward_fill_uprn` propagates values across records at the same premises
3. **Latest-check computation**: `fetch_latest_checks` aggregates across all records at a premises
4. **Vacancy gap-fill**: `fix_premises_dates` generates new `'Vacant Property'` rows to fill gaps in premises timelines, using cross-row date analysis

An incremental approach would miss these cross-row effects and produce inconsistent output.

## S3 Archive Structure

```
s3://hsds-data/ldc/
├── initial_load/                              ← One-time baseline
│   └── ldc_baseline_YYYYMMDD.parquet         (195 columns, all sources)
│
├── snowflake_snapshots/                       ← Monthly raw archives
│   ├── year=2026/
│   │   ├── month=01/
│   │   │   └── current.parquet               (162 columns, as received)
│   │   ├── month=02/
│   │   │   └── current.parquet
│   │   └── ...
│   └── year=2027/
│       └── ...
│
└── clean_archives/                            ← Monthly clean snapshots
    ├── year=2026/
    │   ├── month=01/
    │   │   └── current.parquet               (38 columns, transformed)
    │   ├── month=02/
    │   │   └── current.parquet
    │   └── ...
    └── year=2027/
        └── ...
```

### Athena Access via Glue Crawlers

Three Glue crawlers auto-discover schema from S3 archives:

| Crawler | S3 Path | Athena Database | Table Prefix | Schedule |
|---------|---------|-----------------|--------------|----------|
| `ldc-baseline-crawler` | `ldc/initial_load/` | `ldc_premises` | `baseline_` | One-time |
| `ldc-snapshots-crawler` | `ldc/snowflake_snapshots/` | `ldc_premises` | `snapshots_` | Monthly |
| `ldc-clean-crawler` | `ldc/clean_archives/` | `ldc_premises` | `clean_` | Monthly |

### Example Athena Queries

```sql
-- Compare this month's snapshot vs last month
SELECT year, month, COUNT(*) as row_count
FROM ldc_premises.snapshots_snowflake_snapshots
GROUP BY year, month
ORDER BY year DESC, month DESC;

-- Find businesses that closed between snapshots
SELECT a.tenant_id, a.tenant, a.premises_id
FROM ldc_premises.snapshots_snowflake_snapshots a
LEFT JOIN ldc_premises.snapshots_snowflake_snapshots b
  ON a.tenant_id = b.tenant_id
  AND a.premises_id = b.premises_id
  AND b.year = 2026 AND b.month = 6
WHERE a.year = 2026 AND a.month = 5
  AND b.tenant_id IS NULL;

-- Audit initial baseline against current clean
SELECT COUNT(*) FROM ldc_premises.baseline_initial_load;
SELECT COUNT(*) FROM ldc_premises.clean_clean_archives
WHERE year = 2026 AND month = 6;
```

## Monitoring & Observability

### Logging & CloudWatch

The pipeline uses Python's `logging` module. CloudWatch captures all stdout/stderr from the AWS Batch container, so log messages are automatically available in CloudWatch Logs.

Each pipeline step logs structured messages:

```
2026-05-01 01:00:15 - ldc_premises_e2e - INFO - ============================================================
2026-05-01 01:00:15 - ldc_premises_e2e - INFO - STEP 5: Upserting to PostgreSQL raw table
2026-05-01 01:00:15 - ldc_premises_e2e - INFO - ============================================================
2026-05-01 01:00:15 - ldc_premises_e2e - INFO - Starting upsert of 895,000 rows to gisapdata.ldc_premises_raw
2026-05-01 01:01:20 - ldc_premises_e2e - INFO - Loaded 895,000 rows to staging table
2026-05-01 01:02:30 - ldc_premises_e2e - INFO - Upsert complete: 17,544 rows affected
```

The pipeline also returns a `stats` dictionary at completion with step-level metrics (row counts, validation results, timestamps) which can be inspected in CloudWatch Logs or Step Functions execution output.

## Error Handling & Recovery

### Pipeline STOP Gates

| Gate | Trigger | Effect | Recovery |
|------|---------|--------|----------|
| Suite 1 fail | Source schema invalid | Pipeline aborts before any data written | Check Snowflake schema; alert LDC if breaking change |
| Suite 4 fail | Clean output invalid | Pipeline aborts before publishing clean data | Investigate transformation logic; raw data preserved |

**LDC Data Flow Summary**:
- **Monthly Cadence**: Single AWS Batch job triggered by Step Functions
- **12-Step Pipeline**: Fetch → Validate → Archive → Upsert → Transform → Validate → Publish → Archive
- **Dual Gate Validation**: 2 STOP gates (source schema + clean output), 2 WARN gates (raw quality + business logic)
- **Gap-Proof Architecture**: Accumulated raw table + S3 snapshots ensure no data loss
- **Full Idempotency**: Every step safe to re-run without side effects
