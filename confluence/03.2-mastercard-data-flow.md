# Mastercard Transaction Data Flow - Detailed Workflow

## 💳 **Overview**

The Mastercard Transaction data workflow is a monthly automated process that processes aggregated transaction data from Mastercard Data & Services, applies sophisticated adjustment factors, performs geographic aggregation, and generates economic insights for London's commercial areas. This workflow requires manual file management for data ingestion and uses AWS Step Functions with sequential job execution to ensure proper data processing order.

## 🔧 **Manual Steps Required**

### **Pre-Processing File Management**
**Before triggering the workflow**: Manually download files from Mastercard SFTP server, and upload the zipped and extracted data to S3 buckets.

#### **Step 1: Download from Mastercard SFTP**
- **Source**: Mastercard secure SFTP server (provided monthly)
- **File Types**: 3-hourly data, weekly data(zoom 18 and 15) weekend and weekday data, spending pulse data.
- **Format**: Compressed CSV files
- **Authentication**: Secure SFTP credentials and SSH keys

#### **Step 2: Upload to S3 Storage**
**Required S3 destinations**:

| Data Type | S3 Bucket Path | File Content | Expected Size | Expected Size extracted |
|-----------|----------------|--------------|---------------|---------------|
| **3-Hourly Raw** | `s3://hsds-data/mastercard/mrli_3hourly/raw/` | threehourly quad level data | ~1.5GB | ~5.0GB |
| **Weekly Staging** | `s3://hsds-data/mastercard/weekly/raw/mcard_staging/` |  weekly spend quad level data(zoom 18) | ~80MB | ~1.0GB |
| **Spending Pulse** | `s3://hsds-data/mastercard/spendingpulse/received/` | Market adjustment factors | ~40KB |

#### **File Naming Convention**
```
3-hourly: Geogrids_Custom_GLA_18_Zoom_YYYYMMDD_YYYYMMDD_3hr_timeslot.zip
Weekly: Geogrids_GLA_18_Zoom_YYYYMMDD_YYYYMMDD_Weekdays.zip, Geogrids_GLA_18_Zoom_YYYYMMDD_YYYYMMDD_Weekdays.csv
Spending Pulse: SpendingPulse_England_YTDYYYY_Monthname.csv (example: SpendingPulse_England_YTD2025_July.csv)
```

#### **Upload Verification**

aws s3 ls s3://hsds-data/mastercard/weekly/raw/mcard_staging/ --recursive

## 📅 **AWS Step Functions Workflow Structure**

### **Step Functions Orchestration** (Sequential Execution)
```
AWS Step Functions Manual Trigger
└─ Sequential Processing Chain:
   ├─ 1. Lookup Job (hsds-lookup-job:1)
   │    └─ Purpose: Update spatial lookup tables
   ├─ 2. Weekly Batch Job (hsds-mcard-weekly:1)  
   │    └─ Purpose: Process weekly aggregations + adjustments
   ├─ 3. Weekly Intl Batch Job (hsds-mcard-intl:1)
   │    └─ Purpose: Process international card data
   └─ 4. Threehourly Batch Job (hsds-mcard-3hourly:2)
        └─ Purpose: Process detailed 3-hourly data
```

## 📊 **Sequential Job Processing**

### **Job 1: Lookup Maintenance**
**Job Definition**: `hsds-lookup-job:1`
**Purpose**: Update spatial relationship tables before data processing

**Script**: `highstreets/aws_pipeline/mcard_lookups.py`
- **Process**: 
  - Execute `lookup_manager.process_borough_hs_lookup()`
  - Update `econ_busyness_borough_hs_lookup_3` table
  - Generate all quad lookup tables via `lookup_manager.generate_all_quad_lookups()`
- **Output**: Updated spatial relationship tables for Mastercard quad-to-boundary mappings
- **Duration**: ~15 minutes
- **Dependencies**: None (first job in sequence)

### **Job 2: Weekly Data Processing**
**Job Definition**: `hsds-mcard-weekly:1`
**Purpose**: Process weekly aggregated Mastercard data with market adjustments and partner exports

**Script**: `highstreets/aws_pipeline/mcard_weekly.py`
- **Data Source**: S3 staging directory `mastercard/weekly/raw/mcard_staging/`
- **Process**:
  - Load and clean raw weekly data into PostgreSQL tables by zoom level
  - Generate adjustment factors using Spending Pulse data
  - Aggregate data across all geographic layers (BIDs, high streets, town centres, etc.)
  - Apply inflation adjustments using CPI data
  - Generate partner-specific exports (Colliers, Fitzrovia, Knightsbridge)
  - Upload to London Datastore and PostgreSQL tables
- **Output**: Weekly transaction data by geographic boundary with YoY calculations

### **Job 3: International Data Processing**
**Job Definition**: `hsds-mcard-intl:1`  
**Purpose**: Process international card transaction data separately for tourism analysis

**Script**: `highstreets/aws_pipeline/mcard_weekly_intl.py`
- **Input**: International card usage data from PostgreSQL (non-UK issued cards)
- **Process**:
  - Execute SQL queries for each geographic layer (BID, high street, town centre, MSOA, bespoke, CAZ)
  - Apply CPI inflation adjustments to transaction amounts
  - Generate partner-specific international data exports (Colliers)
  - Upload adjusted data to London Datastore
- **Output**: International visitor spending tables with inflation-adjusted amounts
- **Dependencies**: Requires completion of weekly job for lookup tables

### **Job 4: 3-Hourly Data Processing**
**Job Definition**: `hsds-mcard-3hourly:2`
**Purpose**: Process detailed temporal Mastercard transaction data with CPI adjustments

**Script**: `highstreets/aws_pipeline/mcard_3hourly.py`
- **Data Source**: S3 input `mastercard/mrli_3hourly/raw/`
- **Process**:
  - Read latest 3-hourly data via `mcard_3hourly_latest_data_read()`
  - Transform data using `McardTransform.preprocess_mcard_data()`
  - Load CPI data and apply inflation adjustments
  - Generate geographic aggregations for all boundary types
  - Create partner-specific exports (Colliers, Fitzrovia, Knightsbridge, Avison Young, Jon Puleston)
  - Export to S3 by year and upload to London Datastore
- **Output**: 3-hourly transaction data aggregated by geographic boundaries

#### **Processing Pipeline**

##### **1. Inflation Adjustment**
```sql
-- Apply CPI inflation adjustment to 2018 baseline
UPDATE staging.mastercard_3hourly m3h
SET txn_amt_inflation_adj = txn_amt_adjusted * (
  SELECT cpi_2018.cpi_index / cpi_current.cpi_index
  FROM gisapdata.econ_busyness_cpih_table cpi_2018
  CROSS JOIN gisapdata.econ_busyness_cpih_table cpi_current
  WHERE cpi_2018.yr = 2018 AND cpi_2018.month = 1 
    AND cpi_2018.aggregate = 'CPIH OVERALL INDEX'
    AND cpi_current.yr = EXTRACT(YEAR FROM m3h.count_date)
    AND cpi_current.month = EXTRACT(MONTH FROM m3h.count_date)
    AND cpi_current.aggregate = CASE 
        WHEN m3h.category = 'retail' THEN 'CPIH OVERALL INDEX'
        WHEN m3h.category = 'eating' THEN 'CPIH: RESTAURANTS & HOTELS'
        WHEN m3h.category = 'apparel' THEN 'CPIH: CLOTHING & FOOTWEAR'
        ELSE 'CPIH OVERALL INDEX'
    END
);
```

##### **2. Geographic & Temporal Aggregation**
```sql
-- Generate 3-hourly boundary aggregations
INSERT INTO gisapdata.econ_busyness_mcard_highstreets_3hourly_txn
SELECT 
  hs.highstreet_id,
  hs.highstreet_name,
  m3h.count_date,
  m3h.hours,
  hs.x, hs.y, hs.borough,
  SUM(CASE WHEN m3h.category = 'retail' THEN m3h.txn_amt_inflation_adj ELSE 0 END) as txn_amt_retail,
  SUM(CASE WHEN m3h.category = 'eating' THEN m3h.txn_amt_inflation_adj ELSE 0 END) as txn_amt_eating,
  SUM(CASE WHEN m3h.category = 'apparel' THEN m3h.txn_amt_inflation_adj ELSE 0 END) as txn_amt_apparel,
  SUM(CASE WHEN m3h.category = 'retail' THEN m3h.txn_cnt ELSE 0 END) as txn_cnt_retail,
  SUM(CASE WHEN m3h.category = 'eating' THEN m3h.txn_cnt ELSE 0 END) as txn_cnt_eating,
  SUM(CASE WHEN m3h.category = 'apparel' THEN m3h.txn_cnt ELSE 0 END) as txn_cnt_apparel
FROM staging.mastercard_3hourly m3h
JOIN gisapdata.econ_busyness_mcard_highstreets_quad_lookup lookup 
  ON m3h.quad_id = lookup.quad_id
JOIN gisapdata.highstreet_boundaries hs 
  ON lookup.highstreet_id = hs.highstreet_id
WHERE m3h.txn_amt_inflation_adj IS NOT NULL
GROUP BY hs.highstreet_id, hs.highstreet_name, m3h.count_date, m3h.hours, hs.x, hs.y, hs.borough;
```

##### **3. Year-over-Year Growth Calculations**
```sql
-- Calculate YoY growth rates
INSERT INTO gisapdata.econ_busyness_mcard_highstreets_yoy
SELECT 
  current.highstreet_id,
  current.highstreet_name,
  current.week_start,
  current.yr, current.wk,
  -- Retail growth calculations
  CASE WHEN previous.txn_amt_wd_retail > 0 
       THEN (current.txn_amt_wd_retail - previous.txn_amt_wd_retail) / previous.txn_amt_wd_retail
       ELSE NULL END as yoy_growth_wd_retail,
  CASE WHEN previous.txn_amt_we_retail > 0
       THEN (current.txn_amt_we_retail - previous.txn_amt_we_retail) / previous.txn_amt_we_retail  
       ELSE NULL END as yoy_growth_we_retail,
  current.x, current.y, current.borough
FROM gisapdata.econ_busyness_mcard_highstreets_txn current
LEFT JOIN gisapdata.econ_busyness_mcard_highstreets_txn previous
  ON current.highstreet_id = previous.highstreet_id
  AND current.wk = previous.wk
  AND current.yr = previous.yr + 1;
```

| **Westminster University** | Multiple boundaries | Research datasets | Quarterly |
| **Avison Young** | Town centres + bespoke 249 | Weekly aggregations | Monthly |

#### **Export File Generation**
```sql
-- Colliers HSDS 3-hourly export
SELECT 
  bespoke_area_id,
  name as area_name,
  count_date,
  hours,
  txn_amt_retail,
  txn_amt_eating,
  txn_amt_apparel,
  txn_cnt_retail,
  txn_cnt_eating,
  txn_cnt_apparel
FROM gisapdata.econ_busyness_mcard_bespokes_3hourly_txn
WHERE bespoke_area_id IN (112, 113, 114, 115, 116, 117, 118, 197)
  AND count_date >= DATE_TRUNC('month', CURRENT_DATE - INTERVAL '1 month')
ORDER BY bespoke_area_id, count_date, hours;
```

## 🚨 **Error Handling & Recovery**

### **Step Functions Error Management**
Sequential execution means failure in any job stops the entire workflow:

```json
{
  "Comment": "Mastercard Sequential Processing with Error Handling",
  "Retry": [
    {
      "ErrorEquals": ["States.TaskFailed"],
      "IntervalSeconds": 60,
      "MaxAttempts": 2,
      "BackoffRate": 2.0
    }
  ],
  "Catch": [
    {
      "ErrorEquals": ["States.ALL"],
      "Next": "NotifyFailure"
    }
  ]
}
```

### **Common Issues & Recovery**

#### **S3 File Missing/Corrupted**
**Symptoms**: Job failure at data loading stage
**Resolution**:
1. Verify all required S3 files are uploaded
2. Check file integrity and compression
3. Re-upload corrupted files
4. Restart Step Functions from failed job
