# BT Footfall Data Flow - Detailed Workflow

## 📱 **Overview**

The BT Footfall data workflow is a weekly automated process that collects mobile network analytics data from BT's API, processes it through multiple transformation stages using AWS Step Functions and Batch jobs, and distributes it to internal teams and external partners. This workflow operates with manual parameter configuration to ensure accurate date range processing and uses parallel job execution for efficiency.

## 🔧 **Manual Step Required**

### **Pre-Processing Setup**
**Before triggering the workflow**: Manually configure `startDate` and `endDate` parameters in AWS Step Functions execution input.

**Parameter Format**:
```json
{
  "startDate": "2024-01-15",
  "endDate": "2024-01-21"
}
```

**Date Range Guidelines**:
- **Start Date**: Beginning of the target week (typically Monday)
- **End Date**: End of the target week (typically Sunday)
- **Format**: YYYY-MM-DD
- **Coverage**: 7-day period for complete weekly processing

## 🗓️ **AWS Step Functions Workflow Structure**

### **Step Functions Orchestration** (Parallel Execution)
```
AWS Step Functions Manual Trigger
├─ Branch 1: Secondary Processing Jobs
│  ├─ Lambda: HSDSProcessDateParameters (date validation)
│  └─ Parallel Execution:
│     ├─ Outage Batch Job (hsds-bt-outage-job:1)
│     ├─ MSOA Batch Job (hsds-msoa-job-definition:5)
│     └─ LSOA Batch Job (hsds-lsoa-job:3)
├─ Branch 2: Daily Totals Processing
│  ├─ Date Adjustment (subtract 1 day from start/end dates)
│  └─ Daily Totals Batch Job (hsds-daily-totals-job:2)
├─ Branch 3: Main Hex Processing
│  ├─ Lambda: HSDSProcessDateParameters (date validation)
│  └─ HEX Batch Job (hsds-bt-hex-job:1)
└─ Branch 4: Lookup Maintenance
   └─ Lookup Job (hsds-lookup-job:1)
```

### **Job Queue & Environment**
- **Queue**: `hsds-e2e` (arn:aws:batch:eu-west-2:590183914513:job-queue/hsds-e2e)
- **Compute Environment**: Auto-scaling with container optimization
- **Error Handling**: 3x retry with exponential backoff
- **Monitoring**: CloudWatch integration for real-time status

## 📞 **Data Collection & Processing**

### **Lambda Function: Date Parameter Processing**
**Function**: `HSDSProcessDateParameters` (arn:aws:lambda:eu-west-2:590183914513:function:HSDSProcessDateParameters:$LATEST)

**Purpose**: Validate and format date parameters for downstream Batch jobs
- Input validation for date format and range
- Date arithmetic for daily totals adjustment
- Parameter propagation to container environments

**Error Handling**:
```json
{
  "ErrorEquals": [
    "Lambda.ServiceException",
    "Lambda.AWSLambdaException", 
    "Lambda.SdkClientException",
    "Lambda.TooManyRequestsException"
  ],
  "IntervalSeconds": 1,
  "MaxAttempts": 3,
  "BackoffRate": 2,
  "JitterStrategy": "FULL"
}
```

### **Main Processing: HEX Batch Job**
**Job Definition**: `hsds-bt-hex-job:1`
**Purpose**: Primary BT footfall data collection, transformation, and aggregation

#### **Data Collection Process**
- **API Source**: BT Business API (OAuth authentication)
- **Request Parameters**: Derived from manual input parameters
  - `date_from`: startDate from Step Functions input
  - `date_to`: endDate from Step Functions input
  - `time_period`: 3hourly (fixed)
  - `geography`: TfL_Hex (fixed)
  - `population_type`: all (fixed)

#### **Expected Data Volume**
- **Records**: ~750,000 per week (8,000 hex cells × 7 days × 8 time periods)
- **Format**: JSON with footfall percentages and population estimates
- **Size**: ~150MB compressed JSON response

#### **Transformation Process**
| Transformation | Input Field | Output Field | Validation |
|----------------|-------------|--------------|------------|
| **Time Mapping** | `time_indicator` ("09-12") | `hours` ("09-12") | 8 valid time periods |
| **Date Parsing** | `count_date` (string) | `count_date` (DATE) | Date range validation |
| **Population Calc** | `resident_percentage` + `population_estimate` | `resident` (integer) | Business rule validation |
| **Quality Metrics** | `loyalty_percentage`, `dwell_time` | Direct copy | Range validation |

#### **Output Tables Generated**
| Table Name | Purpose | Record Count |
|------------|---------|--------------|
| `bt_footfall_tfl_hex_3hourly` | Raw hex grid data | ~750,000/week |
| `econ_busyness_bt_highstreets_3hourly_counts` | High street aggregations | ~50,000/week |
| `econ_busyness_bt_towncentres_3hourly_counts` | Town centre aggregations | ~40,000/week |
| `econ_busyness_bt_bids_3hourly_counts` | BID aggregations | ~20,000/week |
| `econ_busyness_bt_bespokes_3hourly_counts` | Bespoke area aggregations | ~15,000/week |

### **Secondary Processing Jobs**

#### **MSOA Batch Job**
**Job Definition**: `hsds-msoa-job-definition:5`
**Purpose**: Aggregate BT data to Middle Super Output Area boundaries

- **Input**: Hex grid data from main processing
- **Process**: Spatial aggregation using hex-to-MSOA lookup tables
- **Output**: `bt_footfall_msoa_3hourly` (~35,000 records/week)
- **Dependencies**: Runs in parallel with main hex processing

#### **LSOA Batch Job**
**Job Definition**: `hsds-lsoa-job:3`
**Purpose**: Aggregate BT data to Lower Super Output Area boundaries

- **Input**: Hex grid data from main processing  
- **Process**: Spatial aggregation using hex-to-LSOA lookup tables
- **Output**: `bt_footfall_lsoa_3hourly` (~150,000 records/week)
- **Dependencies**: Runs in parallel with main hex processing

#### **Outage Batch Job**
**Job Definition**: `hsds-bt-outage-job:1`
**Purpose**: Process BT network outage data for quality assessment

- **Input**: BT outage API data for the specified date range
- **Process**: Outage impact analysis and quality scoring
- **Output**: Outage tracking tables and quality metrics
- **Dependencies**: Independent processing, runs in parallel

#### **Daily Totals Batch Job**
**Job Definition**: `hsds-daily-totals-job:2`
**Purpose**: Generate daily aggregated totals and customer-specific outputs

- **Date Adjustment**: Processes data for (startDate-1) to (endDate-1)
- **Input**: Hex and boundary aggregated data
- **Process**: Daily rollups and customer-specific data preparation
- **Output**: Daily summary tables and customer export files
- **Container Environment Variables**:
  ```
  START_DATE: adjustedStartDate (startDate - 1 day)
  END_DATE: adjustedEndDate (endDate - 1 day)
  ```

#### **Lookup Job**
**Job Definition**: `hsds-lookup-job:1`
**Purpose**: Maintain and update spatial lookup tables

- **Process**: Update hex-to-boundary relationship tables
- **Output**: Updated lookup tables for all boundary types
- **Dependencies**: Independent maintenance job, runs in parallel
- **Frequency**: Every workflow run to ensure data consistency

## 📊 **Quality Assurance & Validation**

### **Automated Quality Checks**
Each Batch job includes comprehensive validation:

#### **Volume Validation**
```sql
-- Verify expected record counts
SELECT 
  COUNT(*) as total_records,
  COUNT(DISTINCT hex_id) as unique_hexes,
  COUNT(DISTINCT count_date) as unique_dates,
  COUNT(DISTINCT hours) as unique_hours
FROM gisapdata.bt_footfall_tfl_hex_3hourly 
WHERE count_date BETWEEN '{startDate}' AND '{endDate}';

-- Expected: ~750k records, ~8k hexes, 7 dates, 8 hours
```

#### **Business Rule Validation**
```sql
-- Population consistency checks
SELECT COUNT(*) as violations
FROM gisapdata.bt_footfall_tfl_hex_3hourly
WHERE (resident + visitor + worker) > population_estimate * 1.05  -- Allow 5% variance
  AND count_date BETWEEN '{startDate}' AND '{endDate}';
```

#### **Spatial Coverage Validation**
```sql
-- Verify London hex coverage
SELECT 
  COUNT(DISTINCT hex_id) as data_hexes,
  (SELECT COUNT(*) FROM hex_grid_reference) as total_london_hexes,
  ROUND(COUNT(DISTINCT hex_id) * 100.0 / (SELECT COUNT(*) FROM hex_grid_reference), 2) as coverage_percent
FROM gisapdata.bt_footfall_tfl_hex_3hourly
WHERE count_date BETWEEN '{startDate}' AND '{endDate}';

-- Expected: >99% coverage
```

### **Cross-Job Validation**
```sql
-- Verify aggregation consistency between hex and boundary tables
WITH hex_totals AS (
  SELECT SUM(resident + visitor + worker) as hex_total
  FROM bt_footfall_tfl_hex_3hourly 
  WHERE count_date BETWEEN '{startDate}' AND '{endDate}'
),
boundary_totals AS (
  SELECT SUM(resident + visitor + worker) as boundary_total
  FROM econ_busyness_bt_highstreets_3hourly_counts
  WHERE count_date BETWEEN '{startDate}' AND '{endDate}'
)
SELECT 
  h.hex_total,
  b.boundary_total,
  ABS(h.hex_total - b.boundary_total) as difference,
  ROUND(ABS(h.hex_total - b.boundary_total) * 100.0 / h.hex_total, 2) as percent_difference
FROM hex_totals h, boundary_totals b;

-- Expected: <5% difference
```

## 🚨 **Error Handling & Recovery**

### **Step Functions Error Handling**
Each job includes automatic retry logic:
```json
{
  "Retry": [
    {
      "ErrorEquals": ["States.TaskFailed"],
      "IntervalSeconds": 30,
      "MaxAttempts": 3,
      "BackoffRate": 2.0
    }
  ]
}
```

### **Common Issues & Resolution**

#### **Date Parameter Errors**
**Symptoms**: Lambda function failures, invalid date ranges
**Resolution**:
1. Verify input parameter format (YYYY-MM-DD)
2. Ensure 7-day range for complete processing
3. Check for weekend/holiday date selection
4. Restart Step Functions with corrected parameters

#### **API Authentication Failures**
**Symptoms**: BT API authentication errors in hex job
**Resolution**:
1. Verify OAuth credentials in container environment
2. Check API token expiration status
3. Retry authentication with backoff
4. Escalate to BT support if persistent

#### **Batch Job Failures**
**Symptoms**: Container failures, resource constraints
**Resolution**:
1. Check CloudWatch logs for specific error messages
2. Verify container resource allocation
3. Restart failed job with same parameters
4. Scale compute environment if resource-related

### **Manual Recovery Procedures**
```bash
# Restart specific failed job
aws batch submit-job \
  --job-name "BT-HEX-Recovery-$(date +%Y%m%d)" \
  --job-queue "hsds-e2e" \
  --job-definition "hsds-bt-hex-job:1" \
  --container-overrides '{
    "environment": [
      {"name": "START_DATE", "value": "2024-01-15"},
      {"name": "END_DATE", "value": "2024-01-21"}
    ]
  }'

# Monitor job status
aws batch describe-jobs --jobs JOB_ID
```
