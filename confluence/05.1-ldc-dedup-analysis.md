# LDC Premises Deduplication Analysis & Change Record

**Author:** Anupam Bose (Data Engineer Analyst, HSDS)
**Date:** May 2026
**Reviewers:** DS Team (Rachel H, Lauren W)

---

## 1. Context

The LDC premises pipeline ingests business history from three sources:
- **live** -- current Snowflake snapshot 
- **historic** -- 10-year Excel time series (~734K rows, 2014-2024)
- **archived** -- older pipeline backups

The existing `all_biz_raw.csv` (1,662,287 rows, 195 columns) is the union of all three. During transformation, `drop_duplicate_rows()` in the original `premises.py` deduplicated and cleaned this into `all_biz_clean.csv` (1,665,502 rows, 38 columns).

When migrating this pipeline into the `highstreets` codebase, we identified that the original deduplication key allowed unintended duplicate primary keys in the clean output, which would break PostgreSQL constraints.

---

## 2. Original Dedup Logic

```python
# premises.py (hsds_datahub -- original DS team code)
all_biz.sort_values(
    by=['timestamp_update', 'date_create', 'date_close', 'tenant_id'],
    ascending=False, na_position='first'
).drop_duplicates(
    subset=['tenant', 'premises_id', 'date_create', 'category', 'tenant_care_of'],
    keep='first'
)
```

**Dedup key:** `(tenant, premises_id, date_create, category, tenant_care_of)`

This key uses the business *name* (`tenant`) rather than LDC's stable identifier (`tenant_id`). The `tenant_care_of` column was included to preserve store-within-store (SWS) records.

---

## 3. Problems Identified

### 3.1 Raw PK Duplicates

The raw CSV contained **6,665 duplicate rows** on the composite PK `(tenant_id, premises_id, date_create)`:

| Kept Source | Dropped Source | Count |
|-------------|---------------|-------|
| live        | archived      | 5,725 |
| historic    | archived      | 940   |

These are stale `archived` snapshots where a `live` or `historic` version of the same record already exists. The `archived` copies are older and superseded.

### 3.2 Clean PK Duplicates

After transformation, the **existing clean CSV** had **11,906 rows** with duplicate PKs (5,953 unique duplicate PKs):

| Category | Unique PKs | % of Total | Description |
|----------|-----------|------------|-------------|
| **Store-within-store (SWS)** | 1,115 | 18.7% | Different `tenant_care_of` (e.g. Fenwick vs Bentalls) |
| **Name changes** | 4,469 | 75.1% | Different `tenant` name (e.g. "Ashoka" → "Ashoka Bearsden") |
| **Source-only diffs** | 368 | 6.2% | Same name, different `source` tag |
| **Other** | 1 | 0.0% | Null-tenant edge case |

### 3.3 Root Cause

Because the old dedup key included `tenant` (name) and `tenant_care_of`, rows where a business was renamed or changed its SWS parent were treated as *different* records despite sharing the same `(tenant_id, premises_id, date_create)`.

### 3.4 Sample Duplicates

| tenant_id | premises_id | date_create | Kept (live) | Dropped (archived) | Category |
|-----------|------------|-------------|-------------|-------------------|----------|
| 14078166 | 50314472 | 2023-03-31 | Mes Pies And Wine | Mes Natural Wines | Name change |
| 12223957 | 52223957 | 2010-02-09 | Ashoka Bearsden | Ashoka | Name change |
| 13844222 | 52601451 | 2021-04-08 | BoConcept (Fenwick) | BoConcept (Bentalls) | SWS parent change |
| 13445166 | 52676227 | 2018-03-22 | Andaz Dining | Lady Abercorn's | Name change |

---

## 4. Review Decision

> "From a data perspective, if a tenant gets renamed -- as far as the data is concerned, that Boots at 123 High St just had a name update. Same business. Dedupe over (tenant_id, premises_id, date_create), deferring to live source."

Specific decisions:

| Scenario | Decision | Rationale |
|----------|----------|-----------|
| **Name changes** | Deduplicate, keep `live` version | Same business, name is mutable; `tenant_id` is the stable identifier |
| **SWS records** | Keep as separate rows | Different `tenant_care_of` distinguishes main premises from concession -- both are real |
| **Source-only diffs** | Deduplicate, keep `live` version | Same record from different pipeline eras; `live` is most current |
| **Null tenant rows** | Keep one if PK is valid | Edge case (2 rows); dedup handles naturally |

---

## 5. New Dedup Logic

```python
# ldc_premises_transform.py (highstreets)
source_priority = {'live': 0, 'historic': 1, 'archived': 2}
all_biz['_src_pri'] = all_biz['source'].map(source_priority).fillna(3)

all_biz.sort_values(
    by=['_src_pri', 'timestamp_update', 'date_create', 'date_close', 'tenant_id'],
    ascending=[True, False, False, False, False],
    na_position='first'
).drop_duplicates(
    subset=['tenant_id', 'premises_id', 'date_create'],
    keep='first'
)
```

**Key changes:**
- **Dedup key**: `(tenant_id, premises_id, date_create)` -- uses stable identifier, not mutable name
- **Sort priority**: `live > historic > archived` added as primary sort, then latest `timestamp_update`
